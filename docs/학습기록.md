# 학습기록

## 1. 문서 목적

이 문서는 `Miso Backoffice v1.0 MVP` 개발 과정에서 각 티켓의 구현 결과를 단순 완료 보고가 아니라 `재현 가능한 학습 자산`으로 남기기 위한 문서다.

이 문서의 목표는 아래와 같다.

- 다음에 같은 기능을 혼자 다시 만들 수 있게 한다.
- 구현 순서와 판단 이유를 잊지 않게 한다.
- 실패와 시행착오까지 자산으로 보관한다.
- 다음 티켓 설계에 바로 반영할 수 있는 운영 지식을 남긴다.

## 2. 기록 원칙

- 모든 `Done` 티켓은 반드시 이 문서의 항목과 연결된다.
- 기록은 커밋 직전 또는 커밋 직후 즉시 작성한다.
- "무엇을 했다"보다 "왜 그렇게 했는가"를 더 중요하게 적는다.
- 코드를 붙여 넣는 대신 구조, 순서, 판단, 대안 비교를 설명한다.
- 기록 품질은 인수인계 수준이 아니라 `강의 수준`을 목표로 한다.

## 3. 강의 수준 기록 기준

좋은 학습기록은 아래 질문에 답할 수 있어야 한다.

- 이 작업은 왜 필요했는가
- 어떤 문제를 먼저 풀어야 했는가
- 구현 순서를 왜 그렇게 잡았는가
- 다른 방법 대신 이 방법을 택한 이유는 무엇인가
- 다시 만들려면 어떤 순서로 따라 하면 되는가
- 다음에 같은 실수를 피하려면 무엇을 체크해야 하는가

즉, 기록을 읽는 미래의 나는 "결과를 전달받는 사람"이 아니라 "수업을 듣고 다시 구현하는 사람"이어야 한다.

## 4. 티켓별 기록 템플릿

아래 템플릿을 모든 완료 티켓에 사용한다.

```md
## [티켓 ID] [작업 이름]

### 1. Objective
이 티켓이 왜 필요했는지 설명한다.

### 2. Output
무엇이 만들어졌는지, 결과물이 무엇인지 정리한다.

### 3. Process
작업을 어떤 순서로 진행했는지 단계별로 적는다.

### 4. Reason
왜 그 구조, 그 도구, 그 순서를 선택했는지 설명한다.

### 5. Concepts
이번 작업에서 이해해야 하는 핵심 개념을 정리한다.

### 6. Pitfalls
실수하거나 놓치기 쉬운 지점, 실제로 막혔던 지점을 적는다.

### 7. Drill
다음에 혼자 다시 연습하려면 어떤 순서로 반복할지 적는다.
```

## 5. 기록 작성 체크리스트

티켓 기록을 남길 때 아래 항목을 확인한다.

- 최종 산출물이 무엇인지 적었는가
- 구현 전에 어떤 판단이 있었는지 적었는가
- 실제 작업 순서를 빠짐없이 적었는가
- 왜 그 선택을 했는지 설명했는가
- 대안이 있었다면 왜 제외했는지 적었는가
- 다음에 반복 가능한 절차로 정리했는가
- 다음 티켓에 영향을 주는 규칙이나 주의사항을 적었는가

## 6. 프로젝트 전용 규칙

이 프로젝트에서는 아래 규칙을 추가로 적용한다.

1. `1티켓 = 1커밋` 원칙을 기준으로 기록한다.
2. 학습기록 제목에는 반드시 티켓 ID를 포함한다.
3. 커밋 단위가 끝났는데 기록이 없으면 티켓은 `Done`이 아니다.
4. 구현 코드 설명보다 먼저 `문제 -> 판단 -> 절차 -> 이유` 순서로 서술한다.
5. 다음 티켓에 바로 영향을 주는 결정은 마지막에 `Next Impact`로 적는다.

## 7. 티켓 기록 영역

아래부터 실제 티켓 완료 후 내용을 누적한다.

---

## [MB-001] 프로젝트 문서 구조와 실행 규칙 정리

### 1. Objective

프로젝트 구현을 시작하기 전에 제품 범위와 운영 규칙을 먼저 문서로 고정하기 위해 수행했다.

이 작업의 핵심 목적은 "무엇을 만들 것인가"보다 먼저 "어떤 기준으로 개발을 진행하고 완료를 판단할 것인가"를 정하는 데 있었다. 초기 단계에서 이 기준이 없으면 이후 구현 티켓의 범위가 흔들리고, 커밋 단위와 학습기록 품질도 일관성을 잃기 쉽다.

### 2. Output

아래 산출물을 정리했다.

- `README.md`에 `v1.0 MVP`의 제품 정의, 문제 정의, 범위, 제외 범위, 성공 기준을 반영했다.
- `docs/티켓단위 개발문서.md`에 Epic 구조와 초기 티켓 세트, 완료 기준, 검증 기준을 정의했다.
- `docs/학습기록.md`에 티켓별 기록 템플릿과 프로젝트 전용 기록 규칙을 준비했다.
- `docs/개발-학습일지 시스템.md`에 현재 프로젝트를 넘어서 재사용 가능한 운영 매뉴얼을 정리했다.

즉, 이 티켓의 결과는 기능 코드가 아니라 앞으로의 개발을 통제하는 기준 문서 세트다.

### 3. Process

작업은 아래 순서로 진행했다.

1. 먼저 이 프로젝트의 첫 제품 버전을 최종 ERP가 아니라 `수급자 관리 흐름 1개를 연결하는 v1.0 MVP`로 정의했다.
2. 그다음 MVP가 반드시 답해야 하는 질문과 포함 범위, 제외 범위를 README 수준에서 명확히 했다.
3. 제품 정의가 고정된 뒤, 이를 실제 실행 가능한 Epic과 Ticket으로 쪼개 `티켓단위 개발문서`에 반영했다.
4. 각 티켓에 Objective, Scope, Out of Scope, Prerequisites, Deliverables, Done Criteria, Verification, Learning Log를 넣어 바로 착수 가능한 수준으로 구체화했다.
5. 마지막으로 `Done`의 의미를 구현 완료가 아니라 `검증 + 문서 반영 + 학습기록 완료`까지 포함하도록 학습기록 문서와 운영 매뉴얼에 연결했다.

### 4. Reason

이 순서를 택한 이유는 구현보다 먼저 범위와 완료 기준을 고정해야 이후 티켓이 흔들리지 않기 때문이다.

- README를 먼저 정리한 이유는 제품의 목표와 MVP 범위를 가장 상위 기준으로 삼기 위해서다.
- 티켓 문서를 그다음에 작성한 이유는 제품 정의가 정해져야 티켓의 Scope와 Out of Scope를 정확히 나눌 수 있기 때문이다.
- 학습기록 문서를 별도로 둔 이유는 개발 결과를 단순 완료 보고가 아니라 재현 가능한 지식 자산으로 남기기 위해서다.
- 운영 매뉴얼을 일반화해서 작성한 이유는 이번 프로젝트에서 생긴 좋은 규칙을 다음 프로젝트에도 바로 복사해 쓸 수 있게 하기 위해서다.

즉, 이 작업은 문서를 늘리기 위한 문서화가 아니라 이후 구현 속도와 일관성을 확보하기 위한 기반 공사에 가깝다.

### 5. Concepts

이번 작업에서 핵심이 되는 개념은 아래와 같다.

- `MVP 범위 고정`: 전체 제품이 아니라 첫 번째로 끝까지 연결할 흐름만 정의하는 것
- `티켓 단위 개발`: 바로 구현 가능한 크기까지 작업을 분해하고 완료 기준을 먼저 적는 방식
- `1티켓 = 1커밋`: 변경 이유와 결과를 커밋 단위에서 명확히 추적하기 위한 규칙
- `Done의 확장 정의`: 코드 작성만이 아니라 검증과 기록까지 완료로 보는 기준
- `학습 자산화`: 결과물을 남기는 데서 끝나지 않고 다음에 스스로 재현 가능한 형태로 지식을 축적하는 것

### 6. Pitfalls

초기 문서 작업에서 특히 주의해야 할 지점은 아래와 같았다.

- 제품 범위를 넓게 잡으면 이후 티켓이 지나치게 커져 바로 구현 가능한 단위가 되지 않는다.
- 티켓 제목만 있고 Done Criteria가 없으면 구현 중간에 범위가 계속 바뀐다.
- 학습기록 템플릿만 만들어 두고 실제 내용을 남기지 않으면 문서상으로만 운영 규칙이 존재하게 된다.
- `Done`을 코드 완료로 오해하면 검증과 기록이 뒤로 밀리고, 결국 다음 티켓에서 같은 판단을 다시 반복하게 된다.

특히 이번 상태에서도 확인됐듯이, 산출물이 이미 있어도 학습기록이 비어 있으면 프로젝트 규칙상 진짜 완료라고 보기 어렵다.

### 7. Drill

다음에 비슷한 프로젝트를 시작할 때는 아래 순서로 반복하면 된다.

1. 프로젝트 목표를 한 문장으로 적는다.
2. MVP가 답해야 할 핵심 질문 3~5개를 적는다.
3. 포함 범위와 제외 범위를 먼저 고정한다.
4. Epic을 나누고, 각 Epic을 바로 구현 가능한 Ticket으로 분해한다.
5. 각 Ticket에 Done Criteria와 Verification을 먼저 적는다.
6. 학습기록 템플릿과 운영 규칙을 준비한다.
7. 첫 티켓부터 `구현 -> 검증 -> 기록` 흐름으로 진행한다.

### 8. Next Impact

다음 티켓인 `MB-002`부터는 실제 구현 준비를 위해 기술 스택, 폴더 구조, 실행 방식, 데이터 저장 전략을 정해야 한다.

중요한 점은 `MB-002`도 단순 선택 나열이 아니라, 이후 `MB-003 수급자 도메인 모델 정의`가 막히지 않도록 기술적 의사결정의 이유와 대안 비교까지 남겨야 한다는 것이다.

## [MB-002] 기술 스택 및 기본 애플리케이션 구조 확정

### 1. Objective

이 티켓의 목적은 기능 구현 전에 사용할 기술과 실행 구조를 확정해, 이후 티켓이 기술 선택 문제로 멈추지 않게 만드는 것이었다.

특히 이번 프로젝트에서는 개발 속도만큼이나 작업자의 학습과 이해가 중요했기 때문에, "많이 갖춘 스택"보다 "지금 이해 가능한 최소 스택"을 고르는 것이 핵심 기준이 되었다.

### 2. Output

이번 작업에서 아래 결과를 만들었다.

- 프론트엔드, 데이터 저장, 폼, 검증, 서버 상태 관리에 대한 기술 선택 방향을 정리했다.
- 각 기술이 맡는 역할과 선택 이유를 문서 수준에서 설명했다.
- 지금 당장 도입할 것과 이후 티켓에서 단계적으로 도입할 것을 구분했다.
- `MB-003` 이후 티켓이 막히지 않도록 적용 순서를 개발 명세 계획 수준으로 남겼다.

즉, 이번 티켓의 산출물은 실제 코드 셋업이 아니라, 학습 가능한 기술 정의와 적용 계획이다.

### 3. Process

작업은 아래 순서로 진행했다.

1. 먼저 `MB-003` 이후 티켓에 필요한 기술 요구를 정리했다. 핵심은 CRUD 중심 관리 화면, 데이터 모델 정의, 입력 폼, 이후 BaaS 연동이었다.
2. 그다음 빠른 구현과 학습 가능성을 동시에 만족하려면 한 번에 많은 도구를 넣지 말아야 한다고 판단했다.
3. 프론트엔드의 중심은 `Next.js`로 정하고, 스타일링은 결과 확인이 쉬운 `Tailwind CSS`로 고정했다.
4. 데이터 저장 축은 `Supabase`를 선택했지만, 초반 학습 부담을 줄이기 위해 지금 티켓에서는 실제 도입이 아니라 계획 수준으로만 고정했다.
5. 폼과 검증, 서버 상태 관리는 필요가 발생하는 티켓에서 단계적으로 도입하기로 정리했다.
6. 마지막으로 티켓 문서와 학습기록에 선택 이유와 적용 계획을 남겨 `MB-002`를 문서 중심 티켓으로 마무리했다.

### 4. Reason

이번 선택의 핵심 이유는 "결과물도 중요하지만, 내가 나중에 이해하고 다시 만들 수 있어야 한다"는 프로젝트 목표에 맞추기 위해서다.

- `Next.js`를 고른 이유는 React 생태계 안에서 라우팅, 레이아웃, 페이지 구조를 함께 배울 수 있기 때문이다.
- `TypeScript`를 포함한 이유는 이후 수급자, 계약, 라운딩 모델을 타입 기준으로 명확하게 정의하기 위해서다.
- `Tailwind CSS`를 먼저 둔 이유는 시각적 결과와 코드의 관계가 바로 보여 초반 학습에 유리하기 때문이다.
- `Supabase`를 선택한 이유는 직접 백엔드를 처음부터 모두 구현하지 않아도 데이터 저장과 조회 흐름을 실제 서비스 관점에서 배울 수 있기 때문이다.
- `React Hook Form`, `Zod`, `TanStack Query`를 지금 당장 설치하지 않은 이유는 좋은 도구라도 한 번에 많이 넣으면 기술의 역할 구분이 흐려지고 학습 밀도가 떨어지기 때문이다.

즉, 이번 티켓은 "최신 조합"을 모으는 작업이 아니라 "지금 이해 가능한 최소 기반"을 고르는 작업이었다.

### 5. Concepts

이번 작업에서 이해해야 할 핵심 개념은 아래와 같다.

- `프레임워크 선택 기준`: 기능 수보다 다음 티켓을 막지 않는 연결성을 우선하는 판단
- `점진적 도입`: 필요한 순간이 오기 전까지 새로운 도구를 미리 넣지 않는 방식
- `학습 가능한 스택`: 내가 역할과 이유를 설명할 수 있는 수준으로 제한한 기술 조합
- `적용 계획`: 기술을 정한 뒤 실제 구현 티켓에서 어떤 순서로 붙일지 미리 정리하는 것

### 6. Pitfalls

이번 티켓에서 특히 주의해야 할 점은 아래와 같았다.

- 기술을 많이 넣는 것이 곧 좋은 기반은 아니다. 초반에는 오히려 어떤 도구가 무슨 문제를 해결하는지 더 헷갈릴 수 있다.
- 기술 선택 티켓에서 실제 셋업까지 바로 넘어가면, 티켓의 목적이 문서화인지 구현인지 흐려질 수 있다.
- 학습 중심 프로젝트에서는 "설치했다"보다 "왜 골랐고 언제 적용할지 안다"가 더 중요한 성과일 수 있다.

### 7. Drill

비슷한 프로젝트에서 이 작업을 다시 하려면 아래 순서로 반복하면 된다.

1. 다음 2~3개 티켓이 요구하는 기술 조건을 먼저 적는다.
2. 한 번에 꼭 필요한 도구만 남기고 나머지는 후순위로 미룬다.
3. 프레임워크, 스타일링, 데이터 저장 전략을 각각 1개씩만 우선 선택한다.
4. 각 기술의 역할과 선택 이유를 문서에 남긴다.
5. 지금 도입할 기술과 뒤 티켓으로 미룰 기술을 구분한다.
6. 다음 티켓에서 어떤 기술을 어떤 순서로 적용할지 적는다.
7. 왜 지금 이 도구만 정했는지 학습기록에 정리한다.

### 8. Next Impact

다음 티켓인 `MB-003`에서는 실제 수급자 도메인 모델을 정의해야 한다.

이때 중요한 기준은 아래와 같다.

- 먼저 TypeScript 타입 기준으로 수급자 필드를 설계한다.
- `Supabase`는 데이터 저장 전략으로 이미 선택됐지만, 실제 도입 시점은 도메인 모델 구조가 잡힌 뒤 판단한다.
- 폼과 검증 도구는 등록/수정 흐름이 시작되는 `MB-005` 근처에서 도입하는 편이 학습과 구현 모두에 유리하다.

## [MB-003] 수급자 도메인 모델 정의

### 1. Objective

이 티켓의 목적은 수급자 관리 흐름의 기준이 되는 최소 데이터 구조를 먼저 확정하는 것이었다.

`v1.0 MVP`는 수급자 등록, 수정, 목록, 상세, 계약 상태, 라운딩 이력까지 이어져야 한다. 따라서 화면을 먼저 만들기 전에 어떤 필드를 공통 기준으로 삼을지 정하지 않으면 이후 티켓마다 필요한 데이터가 흔들릴 수 있다.

### 2. Output

이번 작업에서 `docs/수급자 도메인 모델.md`를 작성했다.

문서에는 아래 내용이 포함된다.

- 수급자 모델 설계 원칙
- `guardian` 대신 `representative`를 사용하는 용어 결정
- `Recipient` 필드명, 타입 초안, 필수 여부, 한국어 표시명, 설명, 이후 사용처
- TypeScript 타입 초안
- 필수값, 선택값, 중복 기준, 날짜 기준
- 라운딩 이력 연결을 위한 `recipientId` 초안
- 샘플 수급자 데이터 3건
- MB-004, MB-005, MB-006에 미치는 영향

또한 `docs/티켓단위 개발문서.md`에서 `MB-003` 상태를 `Done`으로 변경하고, README 문서 목록에 수급자 도메인 모델 문서를 연결했다.

### 3. Process

작업은 아래 순서로 진행했다.

1. 먼저 MB-003의 Scope와 Done Criteria를 다시 확인했다.
2. 수급자 기본 정보에 필요한 최소 필드를 정리했다.
3. 계약 상태 계산에 필요한 날짜 필드를 서비스 제공 기간과 급여 계약 기간으로 나누었다.
4. `guardian`이라는 필드명이 법정후견인에 가깝게 느껴질 수 있어, 대표 연락자와 의사결정자를 포괄하는 `representative`로 용어를 정했다.
5. 라운딩 이력과의 연결은 업무상 번호가 아니라 내부 ID인 `id`를 기준으로 하기로 했다.
6. 필드별 타입, 필수 여부, 설명, 이후 사용처를 표로 정리했다.
7. 샘플 데이터 3건을 작성해 목록, 상세, 수정, 계약 상태 계산에 필요한 필드가 빠지지 않았는지 검토했다.
8. 티켓 문서, README, 학습기록을 연결해 Done 기준을 맞췄다.

### 4. Reason

이번 구조에서 가장 중요한 판단은 `업무상 식별자`와 `시스템 내부 식별자`를 분리한 것이다.

`longTermCareNumber`는 장기요양 업무에서 수급자를 구분하는 중요한 값이지만 사람이 입력하고 관리하는 값이다. 오타, 정정, 변경 가능성을 고려하면 라운딩 이력 같은 내부 관계 연결의 기준으로 쓰기에는 부담이 있다. 그래서 내부 연결은 `id`로 하고, `longTermCareNumber`는 unique 업무 식별자로 두는 편이 안전하다.

두 번째 판단은 `representative`라는 용어를 선택한 것이다. `guardian`은 법적 보호자나 후견인의 느낌이 강해 가족, 친척, 주요 연락자, 의사결정 담당자를 모두 담기 어렵다. 반면 `representative`는 데이터 필드명으로는 넓게 사용할 수 있고, 화면에서는 `대표 연락자`라고 표시해 실무자가 이해하기 쉽게 만들 수 있다.

세 번째 판단은 계약 관련 날짜를 한 덩어리로 보지 않고 두 축으로 나눈 것이다. `serviceStartDate`, `serviceEndDate`는 실제 장기요양 제공 기간이고, `contractRegisteredDate`, `contractExpiredDate`는 급여 계약 관리 기준이다. 이 구분을 미리 해두면 MB-006에서 상태 계산 규칙을 정의할 때 기준이 더 명확해진다.

### 5. Concepts

이번 작업에서 이해해야 할 핵심 개념은 아래와 같다.

- `도메인 모델`: 화면이나 데이터베이스보다 먼저 업무에서 다루는 핵심 대상을 구조화한 것
- `내부 ID`: 시스템 안에서 관계 연결과 조회를 안정적으로 처리하기 위한 식별자
- `업무상 고유값`: 실제 업무 문서나 절차에서 사람에게 의미 있는 고유 번호
- `필수값과 선택값`: 등록이 막히면 안 되는 정보와 반드시 있어야 하는 정보를 구분하는 기준
- `점진적 모델링`: 모든 필드를 한 번에 넣지 않고, MVP 흐름을 완성하는 데 필요한 최소 구조부터 잡는 방식

### 6. Pitfalls

이번 티켓에서 특히 주의해야 할 지점은 아래와 같았다.

- 장기요양인정번호가 업무상 중요하다고 해서 내부 관계 연결의 기본 키로 사용하면 이후 정정이나 변경에 취약해질 수 있다.
- `guardian` 같은 단어는 개발자에게 익숙해도 실제 업무 맥락에서는 법적 의미가 강하게 읽힐 수 있다.
- 계약 날짜를 하나의 만료일로만 단순화하면 서비스 제공 기간과 급여 계약 기간의 차이를 나중에 다시 풀어야 한다.
- MB-003에서 화면 표시 방식까지 정하려고 하면 MB-004, MB-005의 범위를 침범하게 된다.
- 필드를 너무 많이 추가하면 MVP의 최소 흐름보다 관리 부담이 먼저 커진다.

### 7. Drill

비슷한 도메인 모델 작업을 다시 한다면 아래 순서로 반복하면 된다.

1. 다음 2~3개 티켓이 사용할 공통 데이터를 먼저 확인한다.
2. 업무상 반드시 필요한 필드와 있으면 좋은 필드를 분리한다.
3. 내부 연결용 ID와 업무상 고유값을 따로 둔다.
4. 필드명은 개발 편의뿐 아니라 실제 업무 용어의 뉘앙스까지 확인한다.
5. 필드별 타입, 필수 여부, 설명, 사용처를 표로 적는다.
6. 샘플 데이터 3건 이상을 넣어 목록, 상세, 수정 흐름에 무리가 없는지 본다.
7. 다음 티켓에서 어떤 필드를 먼저 화면에 노출할지 영향도를 남긴다.

### 8. Next Impact

다음 티켓인 `MB-004`에서는 이 모델을 기준으로 목록과 상세 조회를 구현해야 한다.

목록에서는 모든 필드를 한 번에 보여주기보다 `name`, `careGrade`, `phone`, `representativeName`, `representativePhone`, `contractExpiredDate`를 우선 표시하는 방향이 적절하다.

상세 화면은 `Recipient` 모델 전체 필드를 확인할 수 있게 구성하되, 등록과 수정 폼의 검증 도구 도입은 `MB-005`에서 판단한다.

## [MB-004] 수급자 목록 및 상세 조회 구현

### 1. Objective

이 티켓의 목적은 `MB-003`에서 정의한 수급자 도메인 모델을 실제 화면 흐름으로 연결하는 것이었다.

문서상으로 필드 구조가 정리되어 있어도, 실무자가 목록에서 수급자를 찾고 상세 정보를 열어볼 수 없다면 데이터 모델은 아직 제품 기능으로 검증된 상태가 아니다. 따라서 이번 작업에서는 등록이나 수정 없이도 샘플 데이터를 기준으로 목록과 상세 조회가 동작하는 최소 앱을 만드는 데 집중했다.

### 2. Output

이번 작업에서 아래 결과를 만들었다.

- Next.js App Router 기반의 최소 앱 골격을 추가했다.
- `Recipient` 타입과 샘플 수급자 데이터 3건을 `src/lib/recipients.ts`에 작성했다.
- `/recipients` 경로에 수급자 목록 화면을 구현했다.
- `/recipients/[id]` 경로에 수급자 상세 화면을 구현했다.
- 루트 경로 `/`는 수급자 목록으로 이동하게 했다.
- `docs/티켓단위 개발문서.md`에서 `MB-004` 상태와 검증 기준을 갱신했다.

### 3. Process

작업은 아래 순서로 진행했다.

1. 먼저 저장소 상태를 확인해 현재 코드가 없고 문서만 있는 상태임을 확인했다.
2. `MB-004`가 실제 목록과 상세 화면 확인을 Done Criteria로 가지고 있으므로, 최소 Next.js 앱 골격이 필요하다고 판단했다.
3. 앱 초기화 범위가 커지지 않도록 인증, 데이터베이스, 등록/수정 폼은 제외하고 화면 조회에 필요한 파일만 추가했다.
4. `MB-003` 문서의 TypeScript 타입 초안을 그대로 코드로 옮겼다.
5. 문서의 샘플 데이터 3건을 `sampleRecipients`로 옮겨 목록과 상세 화면의 기준 데이터로 사용했다.
6. 목록 화면은 이름, 등급, 연락처, 대표 연락자, 대표 연락처, 계약 만료일을 우선 표시하도록 구성했다.
7. 상세 화면은 `Recipient` 모델 전체 필드를 기본 정보, 대표 연락자, 계약 정보, 관리 정보로 나누어 표시했다.
8. 마지막으로 티켓 문서와 학습기록을 갱신해 이번 티켓의 판단과 다음 영향도를 남겼다.

### 4. Reason

이번 작업에서 가장 중요한 판단은 `앱 초기화`를 별도 대형 작업으로 키우지 않고, `MB-004`를 검증하는 데 필요한 최소 기반으로 제한한 것이다.

현재 저장소에는 Next.js 코드가 없었기 때문에 목록과 상세 조회를 구현하려면 앱 골격이 필요했다. 하지만 이 티켓의 본질은 프로젝트 셋업 전체가 아니라 수급자 조회 흐름이다. 그래서 패키지 설정, App Router, 전역 스타일, 목록/상세 라우트, 샘플 데이터까지만 추가하고 Supabase, 폼 라이브러리, 검증 라이브러리는 도입하지 않았다.

두 번째 판단은 데이터 저장소를 아직 만들지 않고 `src/lib/recipients.ts`에 샘플 데이터를 둔 것이다. `MB-004`는 조회 UI와 라우팅의 구조를 확인하는 단계다. 실제 저장과 수정은 `MB-005`, 계약 상태 계산은 `MB-006`에서 다루므로 지금 데이터베이스를 붙이면 티켓 범위가 흐려진다.

세 번째 판단은 목록과 상세의 정보 밀도를 다르게 둔 것이다. 목록은 빠르게 훑는 화면이므로 핵심 필드만 보여주고, 상세는 개별 수급자 확인 화면이므로 모델 전체 필드를 보여주는 방식이 적절하다.

### 5. Concepts

이번 작업에서 이해해야 할 핵심 개념은 아래와 같다.

- `App Router`: `src/app` 폴더 구조로 URL 경로와 화면 컴포넌트를 연결하는 Next.js 라우팅 방식
- `동적 라우트`: `/recipients/[id]`처럼 URL 일부를 값으로 받아 상세 화면을 구성하는 방식
- `샘플 데이터 기반 검증`: 데이터베이스 없이도 화면 구조와 데이터 사용 방식을 먼저 확인하는 방법
- `목록과 상세의 역할 분리`: 목록은 식별과 선택, 상세는 전체 정보 확인을 담당하게 나누는 설계
- `티켓 범위 통제`: 필요한 기반 작업이 생기더라도 현재 티켓의 목적을 넘는 도구 도입은 미루는 방식

### 6. Pitfalls

이번 티켓에서 특히 주의해야 할 지점은 아래와 같았다.

- 앱 코드가 없는 상태에서 바로 조회 화면을 만들려면 초기화 작업이 필요하지만, 이를 별도 프레임워크 학습 티켓처럼 키우면 `MB-004`의 범위가 흐려질 수 있다.
- 샘플 데이터와 문서의 도메인 모델이 달라지면 이후 `MB-005` 등록/수정 폼에서 필드 기준이 흔들린다.
- 목록에 모든 필드를 넣으면 실무자가 빠르게 훑기 어렵고, 반대로 상세에서 필드를 생략하면 모델 검증이 부족해진다.
- `phone`처럼 선택값인 필드는 화면에서 `미등록` 같은 표시 기준을 정하지 않으면 빈 값처럼 보일 수 있다.
- 조회 티켓에서 저장 기능까지 만들면 다음 티켓의 책임이 사라지고 커밋 단위가 커진다.

### 7. Drill

비슷한 조회 화면 티켓을 다시 수행한다면 아래 순서로 반복하면 된다.

1. 먼저 선행 도메인 모델 문서에서 타입과 샘플 데이터를 확인한다.
2. 앱 실행 골격이 있는지 확인하고, 없다면 현재 티켓 검증에 필요한 최소 골격만 만든다.
3. 타입을 코드로 옮기고 샘플 데이터를 작성한다.
4. 목록 화면에서 사용자가 빠르게 식별해야 하는 필드만 고른다.
5. 상세 화면에서는 모델 전체 필드를 빠짐없이 확인할 수 있게 묶는다.
6. 목록에서 상세로 이동하는 라우팅을 연결한다.
7. 빌드 또는 로컬 실행으로 목록과 상세가 깨지지 않는지 확인한다.
8. 문서와 학습기록에 이번 선택이 다음 티켓에 미치는 영향을 남긴다.

### 8. Next Impact

다음 티켓인 `MB-005`에서는 수급자 등록 및 수정 기능을 구현해야 한다.

현재 `src/lib/recipients.ts`의 `Recipient` 타입과 샘플 데이터가 폼의 기준이 된다. 등록/수정에서는 이 타입을 그대로 사용하되, 필수값 검증과 저장 후 목록 또는 상세에 반영되는 흐름을 추가해야 한다.

폼 검증 도구는 `MB-005`에서 판단하는 것이 적절하다. 특히 필수값, 날짜 순서, 장기요양인정번호 중복 기준은 `docs/수급자 도메인 모델.md`의 유효성 기준을 기준으로 삼아야 한다.
