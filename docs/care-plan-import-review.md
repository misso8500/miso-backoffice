# 롱텀케어 원본 우선 급여제공계획 가져오기

2026-11-04 사용자 설명을 반영한 정책과 구현이다. 과거의 반기 초과·중복 적용기간을 내부 업무 방식에 맞춰 교정하지 않는다. 롱텀케어에서 받은 데이터를 원본으로 저장하고, 그 위에서 센터의 상세 내용 작성과 앞으로의 반기 업무를 진행한다.

## 사용 방법

수급자 기초정보 상단 **롱텀케어 계획 가져오기** → `.xlsx` 선택 → 수급자별 매칭·반영 항목 확인 → **선택한 원본·수급자 함께 반영**을 누른다. 같은 수급자의 여러 계획을 함께 선택할 수 있다.

반영 결과에서 **부족한 기초정보 엑셀로 보완**을 누르면 기존 수급자 목록 가져오기로 이어진다. 인정번호 또는 이름+생년월일로 기존 수급자를 찾아 주소·연락처·보호자 등을 채운다. **수급자별 계획·상세 내용 확인**에서는 날짜가 채워진 계획의 **상세 내용 보완**으로 서비스 내용만 작성한다. 정보 보완 필요 명단에는 비활성 상태로 복원한 입력 중 수급자도 포함한다.

새 수급자는 기초정보 입력 중으로 등록한다. 정확히 일치하는 삭제 기록이 있으면 기존 ID를 복원해 과거 연결을 보존한다. 기존 담당자·연락처·건강/돌봄 메모·등록 완료 여부·서비스 정지·활성 상태는 유지한다. 새 수급자를 월별 서비스 명단에 자동 선택하지 않는다.

## 원본과 내부 업무의 구분

- 원본 계획의 시작·종료일을 자르거나 반기로 분할하지 않는다. 겹치는 원본 계획도 모두 보존하며 원본 적용기간에 따라 표시한다.
- 동일 시작일의 원본은 원본 작성일·통보일·계획서 번호로 순서를 정한다. 과거 계획의 상세 메모를 나중에 수정했다고 그 계획이 더 최신 원본이 되지 않는다.
- 원본 적용기간과 실제 통보일 유무, 상세 내용 입력 여부를 별도로 표시한다. 통보일이 없어도 유효한 원본 적용기간이 사라지지 않는다. 미입력 날짜는 원본 표기와 함께 보존하고 미확인으로 표시한다.
- 방문요양과 방문목욕은 별개 계획으로 보존한다. 방문목욕이 방문요양 현재 계획을 대체하지 않는다.
- 상세 내용은 빈 상태로 가져온다. 기존 메모는 보관하고, 원본에 없는 서비스 목표나 욕구사정 결과를 만들어 채우지 않는다.
- 내부 신규/정기 계획의 반기 일정은 그대로 사용하되 **센터 반기 업무 일정**으로 구분한다. 원본 계획에 내부 반기 검증이나 내부 작성 완료 기준을 적용하지 않는다.
- 원본의 날짜·식별자는 상세 보완 화면에서 바꾸지 않는다. 외부 내역 갱신은 원본 재업로드로 처리한다. 메모 보완은 새 이력으로 남기고 원본 스냅샷을 보존한다.
- 원본 전체 열(동의 정보 포함), 파일명·행·가져온 시각을 보관한다. 계획 상세의 **원본 전체 항목·출처 보기**에서 확인한다.

## 매칭과 수급자 정보

인정번호가 일치하면 이름·생년월일까지 확인한다. 번호가 없으면 이름+생년월일의 유일한 일치를 사용한다. 활성/보관 명부를 먼저 확인하고 삭제된 기록까지 찾는다. 다른 사람과 번호가 충돌하거나 같은 인적사항에 서로 다른 원본 번호가 있으면 반영을 막고 확인할 내용을 표시한다.

수급자 이름·생년월일·인정번호·등급·계약일자는 파일 내 최신 계약 기록을 기준으로 미리보기에서 비교한다. 과거 계획을 선택한다고 현재 계약을 과거 행으로 되돌리지 않는다. 빈 날짜·유효하지 않은 등급은 기초정보를 지우지 않고 계획 원본에만 보존한다. 이용계약 변경/명부 복원은 기존 계약 이력에도 기록한다.

부족한 정보는 공통 기초정보 등록 기준으로 계산한다. 주소·대표 연락자 등 원본에 없는 필수정보는 결과 화면과 수급자별 안내에 표시하며 수급자 목록 업로드로 이어서 보완한다.

## 데이터와 API

`POST /api/work/care-plan-import/preview`에 파일명과 base64 파일을 보내 수급자별 신규/연결/복원, 기초정보 변경, 계획 원본 추가/갱신/변경 없음, 부족한 항목을 확인한다.

`POST /api/work/care-plan-import/apply`에는 같은 파일과 `fingerprint`, `selectedKeys`를 보낸다. 재대조, 수급자 신규/복원/인정번호 보완, 기초정보 변경, 계획 버전 추가를 한 트랜잭션으로 처리한다. 미리보기 이후 변경이 있으면 409로 거부하고 입력 파일과 선택을 화면에 유지한다. PostgreSQL에서는 명부/수급자 행을 잠가 일반 계획 저장과도 충돌을 제어한다.

`recipient_plans.schedule.external`에 원본 메타데이터를, `recipient_plan_imports`에 원본 식별자·해시·연결 수급자/논리 계획 ID를 저장한다. 계획서 번호+급여종류로 중복을 방지하고 파일명이나 행 순서 변경만으로 계획을 중복 생성하지 않는다. 번호가 없는 원본은 원본 식별정보 기반 참고 이력으로 보존하며 보완 필요를 안내한다. 원본 내용이 바뀌면 같은 논리 계획에 새 버전을 추가하고 사용자가 작성한 상세 메모를 유지한다. 동일 파일 재업로드는 새 계획 버전을 만들지 않는다.

SQLite/PG 스키마에 가져오기 연결 테이블을 추가했다. PostgreSQL은 기존 테이블과 동일하게 RLS와 직접 접근 제한을 적용한다. **새 버전의 서버와 화면을 먼저 적용한 뒤 원본을 가져온다.** 구버전은 외부 원본 일정과 미확인 날짜를 해석하지 못할 수 있다.

## 이번 파일의 실제 미리보기

운영 DB에 반영하지 않고 읽기 전용으로 대조한 결과다.

| 대상 | 결과 |
|---|---:|
| 파일 | 84명 / 계획 211건 |
| 방문요양 / 방문목욕 | 207건 / 4건 |
| 신규 수급자 | 26명 |
| 삭제된 명부에서 복원 | 7명 |
| 기존 명부 인정번호 보완 | 25명 |
| 복원 명부 포함 인정번호 보완 합계 | 32명 |
| 식별 충돌·반영 불가 | 0건 |
| 반영 후 기초정보 보완 대상 예상 | 62명 |

제공 파일 전체를 임시 DB에 실제 반영해 84명·211건을 보존하는 검증을 통과했다. 운영 DB는 아직 변경하지 않았다. 운영 미리보기는 `handoff/longtermcare-plan-import-preview/preview.json`과 `summary.json`에 있다.

## 검증과 운영 도구

- `tests/care-plan-import.test.mjs`: SQLite/PG 어댑터의 신규/복원/번호 채움, 중복 적용 방지, 원본 업데이트 시 상세 메모 보존, 식별 충돌, 전체 롤백, 원본 적용기간 겹침·미확인 날짜 보존, 제공 파일 84명·211건 실제 임시 DB 반영.
- `tests/care-plan-import-ui.mjs`: PC/모바일 실제 임시 API에서 가져오기·후속 목록 업로드 연결·상세 보완·재업로드 시 입력 보존·넘침 확인.
- 기존 `recipient-plans`, `care-plan-schedule`, `recipient-import` 테스트로 내부 계획과 기초정보 가져오기 회귀를 확인한다.
- `scripts/import-longtermcare-plans.mjs`: 기본은 `BEGIN READ ONLY` 미리보기다. 명시적 `--apply --fingerprint <미리보기 값>`으로 실행할 때만 원본 파일과 변경 전 명부/계획/계약 이력/삭제 기록/가져오기 연결을 `handoff`에 백업하고 적용한다. 이번 작업에서는 운영 반영 모드를 실행하지 않았다.
- `scripts/review-care-plan-import.mjs`: 최초 검토용 읽기 전용 감사 도구. 초기 결과의 ‘현재 명부에서 미매칭 33명’은 이후 26명 신규+7명 복원으로 구분했다. 최초의 반기 제한 차이 집계는 원본 오류나 가져오기 제외 사유가 아니다.
