# 센터 업무 생성 QA

## 확인한 원인과 수정

- 월간 업무 중복 판정이 날짜 단위였다. 월간 업무는 설계 ID + 연월을 기준으로 재사용하도록 변경했다. 시작일·담당자·관련자가 바뀌어도 같은 달의 같은 설계는 기존 묶음을 반환한다. 템플릿 행 잠금과 고유 생성 키로 동시 요청을 방어한다.
- 지도와 설계 화면이 같은 실행 버튼을 노출했다. 실행 생성은 지도에서만 제공하고, 설계에서는 절차 저장·수정만 제공한다. 지도에서 설계를 새로 추가하는 버튼도 제거했다.
- 지도 상단의 점검일·담당자·강조 조건을 제거하고 조회 월만 남겼다. 시작일·기한·담당자는 선택한 업무의 생성 영역에서 입력한다. 생성 시각은 서버가 기록한다.
- 절차 설명과 수행 기록은 기본적으로 접고, 업무를 선택하기 전에는 빈 작업 패널을 표시하지 않는다. 기존 월간 업무는 ‘업무 열기’로 표시하고 POST 없이 열린다.
- 생성·설계 저장·완료 후 전체 지도 재조회 대신 서버 응답으로 해당 항목과 신호등을 갱신한다. 저장 도중 연속 클릭은 클라이언트 잠금으로 막는다. 투두 체크 후에는 수행 기록 영역만 갱신한다.
- 반복 생성은 현재 달의 기존 수행 묶음을 한 번 조회하고, 없는 묶음을 최대 200개씩 일괄 저장한다. HTTP 지도 조회에서 자동 생성과 조회를 한 트랜잭션으로 합쳤다.

## 검증

- SQLite 및 PostgreSQL 어댑터 테스트: 같은 월의 서로 다른 시작일·담당자·관련자 요청이 같은 ID를 반환하고 월간 묶음이 하나만 남는다.
- 생성 비용 테스트: 반복 설계 10개, 평일 22회씩 총 220개 생성에서 조회 2회, 일괄 INSERT 2회. 실제 운영 서버의 왕복 시간이나 PostgreSQL 처리 시간을 측정한 수치는 아니다.
- 데스크톱·모바일 브라우저: 생성 버튼 동시 2회 클릭 시 POST 1회, 생성 후 GET 추가 요청 없음, 기존 월간 업무 열기 시 POST 없음, 설계 화면에서 실행 생성 UI 없음, 관계자 연결·단계 설정·투두 체크 동작 검증.
- 전체 자동 테스트 143개 통과. 실제 운영 PostgreSQL의 응답 시간은 추가 계측이 필요하다.

## 데이터 보존

이전에 이미 생성된 중복 묶음은 완료 이력 손실을 피하기 위해 자동 삭제·병합하지 않는다. 기존 월간 기록이 여러 개라면 시작일과 ID 순으로 첫 기록을 대표로 열며, 새 중복 생성을 막는다. 데이터 정리는 별도 검토가 필요하다.
