# 수급자 기초정보 — 연락과 방문 중심 조회

잠재고객 관리와 같은 명단·상세 패널 스타일을 적용한다. 사회복지사가 자주 확인하는 이름·등급·연락처·주소·주요 연락자·담당자와 계약 상태를 기본 명단에 둔다. 긴 계획 메모와 관리 작업은 선택한 영역에서 확인한다.

## 화면

- **등록 명부 / 기간 확인 필요 / 담당 미배정 / 정보 보완 필요** 카드로 명단을 좁힌다. 등록 명부는 활성 레코드 수이며 실제 서비스 이용 중 인원을 뜻하지 않는다.
- 명단 보기는 **기본·연락처 / 기간·갱신 / 돌봄·계획**으로 구분한다. 계획 명단은 긴 메모 대신 현재 계획 기간과 다음 작성 일정을 표시한다.
- 이름을 누르면 화면 안의 상세 패널이 열린다. 기본은 연락·방문 정보와 이용계약·계획 기간 요약이며, 건강·방문 참고사항과 인정·등록 정보는 펼쳐볼 수 있다.
- **관련 서류**를 선택해야 파일 목록을, **돌봄·계획**을 선택해야 계획과 변경 이력을 조회한다. 기본 상세를 열 때 이 두 요청을 먼저 실행하지 않는다.
- 연락·주소는 짧은 입력 폼으로 직접 수정한다. 전체 등록정보 수정, 담당자·업무식별명, 계약 기간 갱신, 계약해지·복구·삭제는 **계약·관리**에 둔다.
- 서비스 명단과 라운딩 바로가기는 선택한 수급자 ID를 전달한다. 같은 이름이어도 해당 수급자로 범위를 좁힌다. ‘전체 대상 보기’ 또는 검색어 변경으로 범위를 풀 수 있다. 이동만으로 월별 대상자를 선택하거나 방문 계획을 생성하지 않는다.
- 연락처·계획·서류·계약 기간의 미저장 변경은 탭 이동·닫기 전에 확인한다. 저장 중에는 이동을 막는다.

## 연락처 저장

`PUT /api/recipients/:id/contact`는 `phone`, `address`, `representativeName`, `representativeRelation`, `representativePhone`, `updatedAt`만 받는다. 명부·계약·계획·등록 상태는 바꾸지 않는다. 버전이 오래되면 409로 입력을 보존하고, 화면에서 최신 정보를 다시 조회할 수 있다. SQLite와 PostgreSQL 모두 조건부 UPDATE로 동시 수정 충돌을 검사한다. 새 테이블이나 데이터 이관은 필요하지 않다.

## 검증

- `tests/recipient-directory-ui.mjs`: 임시 SQLite API와 실제 앱 메뉴를 사용한 PC·모바일 검증. 간결한 명단, 연락처 저장·충돌 복구, 미완성 수급자 수정, 계획·서류 지연 조회, 미저장 입력 보호, 계약 관리 진입, 동명이인 ID 기반 업무 이동과 가로 넘침 여부를 확인한다.
- `tests/recipient-contact.test.mjs`: 허용 필드만 변경, 계약·건강 정보 보호, 잘못된 입력·오래된 버전 거부, 미완성 등록 상태 유지.
- 기존 계획·서류·서비스 명단·기간 조회 테스트를 함께 실행한다.

## 인정번호·주소·서비스 상태

- 인정번호는 명단과 상세에 표시하며 앞의 `L`을 한 번만 붙인다. 저장값은 변경하지 않는다. 입력 중인 임시 번호는 ‘인정번호 미등록’으로 표시한다.
- 명단과 상세 주소의 복사 버튼은 주소만 복사하며 성공·실패 결과를 안내한다. 주소가 없으면 비활성화한다.
- 담당·계약 상태는 서비스 알림과 공통 신호등을 사용한다. 입력 중은 검정, 종료·일시정지는 빨강, 기존 갱신 기준(만료 60일 이내)은 노랑, 진행 중은 초록이다. 시작 전은 불을 켜지 않고 ‘서비스 시작 예정’으로 안내한다.
- 일시정지는 기존 `recipient_service_pauses`의 미복귀 기록을 SQLite·PostgreSQL 명단/상세 조회에 반영한다. 기초정보 탭으로 돌아오면 상태를 다시 조회한다.
- 번호 형식·신호 우선순위는 `tests/recipient-directory.test.mjs`, 복사 및 실제 정지·복귀 상태 연결은 PC·모바일 UI 테스트에서 검증한다.
