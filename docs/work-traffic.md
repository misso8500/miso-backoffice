# 업무 신호등

## 센터 업무 통합 설계

- 월간·사건형 업무와 매일 반복업무는 같은 태스크 맵 설계와 수행 묶음을 사용한다. 이전의 개인 반복 규칙은 ‘기존 반복 규칙’에서 그대로 관리한다. 기존 데이터를 추측하여 합치거나 삭제하지 않는다.
- 매일 반복업무는 조회 시 서울 기준 이번 달의 시작일~오늘 범위에서 해당 요일의 묶음을 생성한다. 미래 일자·월간 업무는 자동 생성하지 않는다. 서버 예약 작업은 아니며 앱에서 업무를 조회할 때 생성한다.
- 매월 업무는 전체지도에서 ‘이번 달 업무 생성·열기’를 눌러 점검일에 해당하는 묶음을 생성한다. 현재 달의 마감일 전에 완료할 수 있고, 그 경우 실제 수행일은 체크한 오늘로 기록한다.
- 단계마다 기본 담당자와 기준일 이후 0~365일의 완료 기한을 설정할 수 있다. 미지정 담당자는 묶음 담당자를 따른다. 생성 시 단계별 담당자·기한을 복사하므로 이후 설계 변경이 기존 수행 묶음을 바꾸지 않는다.
- 사건형 업무는 수급자·근로자 최대 30명을 함께 연결한다. 동일 대상의 선택 순서나 묶음 담당자가 달라도 같은 설계·기준일·대상 조합은 중복 생성하지 않는다. 기존 형식의 수행 묶음도 재사용한다.
- 반복 활성화 변경은 적용 시작일과 이전 기준을 보존한다. 중지 시 이미 생성된 업무를 지우지 않는다. 하위 단계별 기한 경과도 전체 신호등에 반영하며 대체 담당자의 공통 점검 완료도 인정한다.
- 투두의 담당자·상태·검색 조건은 각 단계에 적용하고, 완료는 해당 단계 담당자의 수행 기록으로 저장한다. 체크한 계정은 별도로 남긴다.

공동 업무의 업무 신호등 탭은 고정 카테고리 → 업무 설계 → 날짜별 수행 묶음 → 하위 단계로 구성한다. 담당자 필터는 지도를 재배치하지 않고 해당하지 않는 가지를 흐리게 표시한다. 수행 기록은 접어서 보관한다.

## 저장과 집계

- `work_map_templates.payload`: 유형(daily/monthly/event), 분류, 단계 ID·처리 방법, 생성일, 담당자·적용 시작일·점검 요일, 월 점검일, 이전 점검 기준(scheduleHistory). version으로 동시 수정을 검사한다.
- `work_map_runs.payload`: templateId·templateVersion, 설계 당시 절차 스냅샷, 시작일·기한, 담당자·관련자, 단계별 완료 시각·완료 계정 ID·표시 이름·수행 기록 ID. 설계 수정은 이미 수임한 절차를 바꾸지 않는다.
- 기존 templateId가 없는 수행 묶음은 저장된 run_key의 설계 ID로 읽기 시 연결한다. 기존 설계는 점검 기준을 설정하기 전까지 수임한 건만 집계한다.
- 동일 설계·날짜·담당자·연결 대상은 중복 생성하지 않는다. 단계 완료와 업무일지 수행 기록·이력은 하나의 DB 트랜잭션으로 저장한다.
- 월 조회: `GET /api/work/task-maps?month=YYYY-MM`. 서버가 서울 날짜 기준으로 신호등과 날짜별 상태를 계산한다. 클라이언트가 집계 상태를 별도로 저장하지 않는다.

## 신호등 기준

- 빨강: 오늘 이전의 미수행 점검일 또는 기한이 지난 미완료 업무.
- 노랑: 오늘 점검이 남았거나 진행 중인 묶음이 있음.
- 초록: 오늘까지 필요한 점검과 해당 기간의 진행 업무가 완료됨. 미래 점검까지 완료했다는 의미가 아니다.
- 모두 꺼짐: 아직 점검 시점이 오지 않았거나 발생한 업무가 없음.

일일 점검은 지정 요일마다 한 회, 월간 점검은 지정일 한 회를 기대하며 월말을 넘는 점검일은 말일로 보정한다. 기관 공통 수행은 대체 담당자가 완료해도 정기 점검 완료로 인정한다. 생성하지 않은 날짜도 누락에 포함한다. 비정기 업무는 미완료이면 다음 달에도 이어 보이며 완료한 달까지 남는다.

기준 변경은 오늘 이후 적용한다. 이전 기준을 보존하여 과거 월의 기대 점검일과 담당자가 변경되지 않게 한다. 업무 유형 변경은 별도 설계로 추가한다. 공휴일·휴가는 현재 자동 제외하지 않으며 설정한 요일을 적용한다.

기존 설계에 정기 기준이 없으면 카드의 ‘설계·점검 기준 수정’에서 담당자, 적용일, 요일 또는 월 점검일을 지정한다. SQLite는 API 시작 시 테이블을 준비하며 PostgreSQL은 기존 초기화 절차로 schema.sql을 적용한다.
