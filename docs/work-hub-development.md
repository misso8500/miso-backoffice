# 공동 업무 창구 단계별 개발

## WH-001: 업무 등록부터 공동 조회·수정·취소까지

목적: 카카오톡 지시와 개인 메모를 다시 취합하기 전에, 센터가 같은 업무 목록을 보며 담당자와 기한을 관리한다.

범위:

- 현재 Google 로그인 허용 계정을 공동 업무 구성원으로 연결한다. 최초 로그인 전에는 계정을 구분할 수 있는 이메일을 표시하고, 로그인 시 Google 이름을 반영한다. 기존 수급자 담당자 명부와 이름으로 자동 병합하지 않는다.
- 제목·상세·담당자·기한·센터 업무 분류·수급자/근로계약 관련자를 등록한다. 분류 미정과 담당자 미정도 허용한다.
- 요청자는 서버가 확인한 현재 계정이다. 담당자와 관련자는 다른 관계다. 근로자는 기존 계약 ID 기준으로 연결하고 주민등록번호로 새 업무 식별자를 만들지 않는다.
- API/DB 저장, 담당자별 조회, 수정·취소, 변경 이력, 동시 수정 충돌 방지, 실패 시 입력 보존.
- 관련자 간단 등록은 기존의 수급자/근로계약 초안 저장을 활용한다.

제외: 계획·수행, 주월 캘린더, 완료 판정, 일지/출근부/휴가서류 생성, 알림, 평가 지표 매핑. 이 단계에서는 존재하지 않는 기능의 메뉴를 만들지 않는다.

사용자가 **모두 조회·수정·취소 가능**으로 결정했다. 기존 로그인 허용 계정만 접근하고, 서버가 요청자·수정자를 기록한다. 직책별 승인 기능은 만들지 않는다.

완료 기준:

1. 인증되지 않은 요청은 업무 데이터에 접근할 수 없다.
2. 담당자·관련자의 존재와 입력값을 서버에서 검증한다.
3. 재조회/DB 재연결 후 등록·수정·취소 상태가 유지된다.
4. 다른 사람이 먼저 바꾼 이전 버전은 덮어쓰지 않고 409로 차단한다.
5. 업무와 변경 이벤트는 하나의 트랜잭션으로 저장한다.
6. SQLite 실제 HTTP 검사와 Postgres 저장 경계 검사, 기존 관련 검사 및 빌드 통과.
7. 사용 안내와 학습기록에 설계 이유·제약·검증 결과를 남긴다.

다음 티켓은 WH-002 일간 계획·수행, WH-003 주월 개괄, WH-004 업무일지 연결로 나눈다. 각 단계의 세부 범위는 앞 단계 사용 검토 후 확정한다.

## WH-001 구현 결과

공동 업무 메뉴, 기존 인증 계정 기반 구성원, 제목/담당자/기한/분류/관련자 등록·수정·취소와 이력 조회를 구현했다. 실제 명부 초안 생성도 기존 API를 재사용한다. 전체 92개 검사와 빌드를 통과했다. [사용 안내와 검증 한계](work-hub.md), [설계 학습기록](학습기록.md)을 함께 참고한다.

실제 운영 Postgres와 실제 로그인 브라우저 검토는 미실시다. 운영 DB는 이번 검증에 사용하지 않았다. 자동 커밋·배포·운영 데이터 생성은 하지 않았다.

## WH-001 보완: 고정 담당자 명부

사용자 지정에 따라 담당자는 신수연, 박준규, 황영상 순서로 고정한다. 로그인 계정 명부와 별도의 고정 담당자 테이블·참조 열을 추가해 기존 계정 배정을 보존한다. 요청자·수정자는 여전히 인증 계정이다. 역할은 화면에 표시하지 않는다. 담당자 선택/필터에 같은 순서를 적용하고 관련 검사 6개와 빌드를 통과했다.

## WH-002: 일간 계획과 실제 수행

범위: 날짜 탐색, 세 명의 수행자 선택, 업무의 날짜/오전·오후·미정 계획 배치, 오전/오후 빠른 실행, 계획 없는 수행 입력, 수행 내용/시간대 수정·취소, 계획 취소, 업무 전체 완료/재개. 허용 계정 모두 공동 수정한다. 실제 수행자와 입력한 계정을 분리한다.

완료 기준:

- 날짜·수행자·관련 업무를 서버에서 검증하고 다른 날짜/직원의 기록이 섞이지 않는다.
- 계획과 수행은 서로 다른 레코드이며 업무 전체 완료는 별도 동작이다.
- 같은 계획의 빠른 수행이 중복 생성되지 않고 수정/취소 버전 충돌을 차단한다.
- 계획/수행의 당시 제목·분류·관련자를 스냅샷으로 보존한다. 실제 날짜·시간대와 입력 시각을 구분한다.
- 계획 취소 후 기존 수행은 남는다. 업무 취소는 남은 계획을 취소하되 수행을 지우지 않는다.
- 변경과 변경 이벤트를 같은 트랜잭션으로 저장한다. 재접속 후 복원, 실패 시 원복, 동시 요청을 검사한다.
- 주월 캘린더·공식 서류·근태 확정은 다음 단계로 남긴다.

### WH-002 구현 결과

고정 날짜 탐색, 일간 계획/수행 비교, 계획 배치·취소, 오전/오후 빠른 수행, 직접 수행·내용 수정·취소, 업무 전체 완료/재개, 제목 형광펜과 건수 표시를 구현했다. 전체 99개 검사와 빌드 통과. 실제 운영 DB와 실제 로그인 브라우저 조작은 미검증이며 배포하지 않았다. 다음은 WH-003 주·월 개괄이다.

## WH-003: 주·월간 개괄

범위: 일/주/월 전환, 월요일 기준 주간·월간 달력, 기간 앞뒤 이동, 담당자 필터, 기한/계획/실제 수행 구분, 전체 담당자 보기의 흰색 초성 스티커, 미배치 업무, 날짜/기록에서 일간으로 이동.

완료 기준:

- 기존 업무/계획/수행 테이블을 기간 조회하며 캘린더용 별도 업무 데이터를 만들지 않는다.
- 기간 길이와 담당자 값을 서버에서 검증하고, 취소된 계획·수행과 취소/완료 업무의 기한을 활성 집계에서 제외한다.
- 계획이 없는 진행 업무를 구분하되 다른 기간의 활성 계획을 미배치로 잘못 표시하지 않는다.
- 주 경계·월 경계·윤년·말일 이동을 처리하며 날짜 클릭 후 담당자/일간 맥락을 유지한다.
- 날짜 이동 중 오래된 요청이 새 기간을 덮어쓰지 않는다. 빈 날짜를 결근·업무일지 누락으로 판단하지 않는다.
- 서류 생성과 자동 반복 업무는 다음 범위로 남긴다.

### WH-003 구현 결과

일/주/월 고정 탐색, 주간 7일·월간 6주 조회, 담당자 필터, 흰색 초성 스티커, 기한/계획/수행 구분, 전 기간 활성 계획 유무에 따른 미배치 업무, 날짜·수행자 맥락을 유지하는 일간 이동을 구현했다. 달력 전환 중 업무 입력 초안은 보존한다. 월간 집계는 인접 달을 제외한다.

전체 104개 검사와 TypeScript/Vite 빌드 통과. 인증·기간 제한·인물별 조회·스냅샷·상태 필터·연월 경계·재시작 유지 등을 검사했다. 실제 운영 Postgres와 로그인 브라우저/모바일은 미검증이며 배포하지 않았다. 다음 WH-004는 실제 수행을 업무일지 초안 검토로 연결하는 단계다.
