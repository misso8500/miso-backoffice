# 개발 시스템 및 학습일지 운영 매뉴얼

## 1. 문서 목적

본 문서는 현재 개발 중인 프로젝트에서 사용한 운영 방식을 일반화하여, 앞으로 다른 애플리케이션을 개발할 때도 재사용할 수 있는 개발 시스템과 학습일지 시스템의 기준을 정의한다.

이 문서는 특정 기술 스택 하나에 종속되지 않는 것을 원칙으로 하며, 다음 목표를 가진다.

- 기획에서 구현까지 이어지는 작업 흐름을 표준화한다.
- 작은 단위의 티켓 기반 개발을 가능하게 한다.
- AI 활용 결과물을 단순 생성물이 아니라 재사용 가능한 학습 자산으로 전환한다.
- 프로젝트가 바뀌어도 동일한 운영 습관과 기록 체계를 유지할 수 있게 한다.

---

## 2. 시스템 개요

본 운영 체계는 두 개의 축으로 구성된다.

| 시스템 | 역할 |
|--------|------|
| 개발 시스템 | 무엇을 만들지 정의하고, 어떤 순서로 구현하며, 어떻게 완료를 판단할지 관리 |
| 학습일지 시스템 | 구현 과정에서 얻은 판단 근거, 실수, 재현 절차, 개념 이해를 축적 |

두 시스템은 분리되어 있지만 항상 연결되어야 한다.

- 개발 시스템은 실행 우선 체계다.
- 학습일지 시스템은 재현 가능성 확보 체계다.
- 개발이 끝났더라도 학습일지가 없으면 장기적으로 같은 실수를 반복한다.
- 학습만 남고 실행 기준이 없으면 실제 산출물 속도가 떨어진다.

따라서 모든 작업은 아래 흐름을 따른다.

`기획 -> 티켓화 -> 구현 -> 검증 -> 학습기록 -> 다음 티켓 반영`

## 3. 개발 시스템 정의

### 3.1 핵심 원칙

- 작업은 반드시 작은 단위의 티켓으로 분해한다.
- 티켓은 "바로 구현 가능한 수준"까지 구체화한다.
- 완료 기준이 없는 작업은 시작하지 않는다.
- 기능 구현과 구조 정리는 분리하되, 연결 규칙은 명확히 둔다.
- AI를 사용할 수 있지만, 최종 책임은 프로젝트 운영자에게 있다.
- 코드는 결과물이고, 문서는 판단 기준이다.

### 3.2 개발 단위

모든 작업은 다음 단위 중 하나로 관리한다.

| 단위 | 설명 |
|------|------|
| Epic | 하나의 큰 목표 또는 기능 묶음 |
| Ticket | 실제 착수 가능한 최소 실행 단위 |
| Task | 티켓 내부의 세부 작업 |
| Log | 작업 수행 후 남기는 학습 기록 |

권장 관계는 다음과 같다.

- Epic 1개는 여러 Ticket으로 구성한다.
- Ticket 1개는 필요 시 여러 Task로 나눌 수 있다.
- Ticket 완료 시 Log 1개 이상을 남긴다.

### 3.3 티켓의 필수 구성

각 티켓은 최소한 아래 항목을 포함해야 한다.

- 티켓 ID
- 제목
- 목적
- 작업 범위
- 제외 범위
- 선행 조건
- 산출물
- 완료 기준
- 검증 방법
- 기록 필요 여부

권장 템플릿은 다음과 같다.

```md
## [티켓 ID] [제목]

### 1. Objective
이 티켓을 왜 수행하는가

### 2. Scope
- 포함 작업
- 포함 작업

### 3. Out of Scope
- 이번 티켓에서 하지 않을 것

### 4. Prerequisites
- 선행 티켓 또는 전제 조건

### 5. Deliverables
- 생성 파일
- 구현 기능
- 문서 반영 사항

### 6. Done Criteria
- 어떤 상태가 되면 완료로 볼 것인가

### 7. Verification
- 어떻게 확인할 것인가

### 8. Learning Log
- 기록 필요
- 기록 위치
```

### 3.4 상태 체계

모든 티켓은 아래 상태 중 하나를 가져야 한다.

| 상태 | 의미 |
|------|------|
| Todo | 아직 시작하지 않음 |
| In Progress | 현재 구현 중 |
| Review | 구현 완료, 검토 및 테스트 필요 |
| Done | 검증과 기록까지 완료 |
| Blocked | 외부 이슈 또는 선행 작업 미완료 |
| Archived | 취소되었거나 보류된 티켓 |

핵심 원칙은 다음과 같다.

- `Done`은 코드 작성만으로 달성되지 않는다.
- 테스트 또는 확인이 끝나야 한다.
- 필요한 학습기록까지 남겨야 진짜 완료다.

### 3.5 우선순위 체계

| 우선순위 | 의미 |
|---------|------|
| P0 | 없으면 프로젝트 진행이 막힘 |
| P1 | 핵심 가치 제공에 직접 필요 |
| P2 | 완성도, 유지보수성, 운영성을 높임 |
| P3 | 있으면 좋지만 지금 당장 필요하지 않음 |

### 3.6 작업 흐름

표준 개발 흐름은 다음과 같다.

1. 프로젝트 목표를 1문장으로 정의한다.
2. 목표를 Epic으로 분해한다.
3. Epic을 바로 구현 가능한 Ticket으로 쪼갠다.
4. 각 Ticket에 완료 기준과 검증 방법을 적는다.
5. 구현 전 필요한 데이터 구조, 폴더 구조, 인터페이스를 정한다.
6. 티켓 단위로 구현한다.
7. 검증 후 학습일지에 결과를 남긴다.
8. 배운 내용을 다음 티켓의 설계에 반영한다.

### 3.7 폴더 및 문서 운영 기준

프로젝트마다 이름은 달라도 역할은 유지하는 것이 좋다.

권장 문서 구조는 다음과 같다.

```text
docs/
  프로젝트개요.md
  티켓단위_개발수행문서.md
  학습기록.md
  개발시스템_및_학습일지_운영매뉴얼.md
```

권장 원칙은 다음과 같다.

- `프로젝트개요`는 제품 방향과 범위를 관리한다.
- `티켓단위_개발수행문서`는 실행 계획과 완료 기준을 관리한다.
- `학습기록`은 재현 가능한 학습 자산을 관리한다.
- 운영 매뉴얼은 프로젝트가 달라져도 유지되는 공통 규칙을 관리한다.

### 3.8 AI 활용 규칙

AI를 사용하는 경우에도 작업은 반드시 사람이 이해 가능한 구조로 정리해야 한다.

- AI에게 요청하기 전에 목표와 제약을 먼저 문장으로 적는다.
- 한 번에 큰 결과물을 받기보다 작은 티켓 단위로 요청한다.
- 생성된 코드는 그대로 수용하지 말고 구조와 이유를 해석한다.
- 결과물보다 "왜 이렇게 나왔는가"를 기록한다.
- 다음에 같은 작업을 스스로 재현할 수 없으면 학습이 끝난 것이 아니다.

## 4. 학습일지 시스템 정의

### 4.1 목적

학습일지 시스템은 단순 회고 문서가 아니다.
이 시스템의 목적은 다음과 같다.

- 같은 문제를 다음 프로젝트에서 더 빨리 해결한다.
- AI가 만든 결과를 내 지식으로 전환한다.
- 실패와 시행착오를 자산으로 보관한다.
- 프로젝트 종료 후에도 재사용 가능한 운영 지식을 남긴다.

### 4.2 기록 원칙

- 기록은 티켓 완료 직후 작성한다.
- 결과만 적지 말고 순서와 판단 근거를 적는다.
- 성공 사례뿐 아니라 실패 사례도 남긴다.
- 다시 만들 수 없는 기록은 좋은 기록이 아니다.
- 개념, 실수, 재현법, 다음 개선점을 함께 남긴다.

### 4.3 학습일지의 최소 구조

모든 학습 기록은 아래 구조를 기준으로 작성한다.

```md
## [티켓 ID] [작업 이름]

### 1. Objective
무엇을 위해 작업했는가

### 2. Output
무엇이 만들어졌는가

### 3. Process
어떤 순서로 진행했는가

### 4. Reason
왜 그런 선택을 했는가

### 5. Concepts
핵심 개념은 무엇인가

### 6. Pitfalls
실수하기 쉬운 지점은 무엇인가

### 7. Drill
다시 연습하려면 어떻게 할 것인가
```

### 4.4 반드시 남겨야 하는 정보

- 최종 산출물
- 사용한 도구와 환경
- 핵심 구현 순서
- 선택한 구조의 이유
- 대안과 비교했을 때의 장단점
- 막혔던 지점과 해결 방법
- 다음 프로젝트에 그대로 적용 가능한 규칙

### 4.5 좋은 기록의 기준

좋은 학습 기록은 다음 질문에 답할 수 있어야 한다.

- 이 작업을 왜 했는가
- 무엇을 만들었는가
- 어떤 순서로 만들었는가
- 왜 그 방법을 택했는가
- 다음에도 혼자 다시 만들 수 있는가

### 4.6 나쁜 기록의 예

- "완료함"처럼 결과만 적은 기록
- 코드 조각만 있고 설명이 없는 기록
- AI 답변을 그대로 붙여 넣은 기록
- 무엇이 핵심 판단이었는지 드러나지 않는 기록
- 다음에 참고할 체크포인트가 없는 기록

## 5. 개발 시스템과 학습일지 시스템의 연결 규칙

두 시스템은 아래 규칙으로 연결한다.

### 규칙 1

모든 `Done` 티켓은 학습일지 항목과 연결되어야 한다.

### 규칙 2

학습일지에는 티켓 ID를 반드시 남긴다.

### 규칙 3

하나의 티켓에서 중요한 판단이 있었다면, 다음 티켓의 설계에 그 내용을 반영한다.

### 규칙 4

반복되는 실수는 학습일지에만 남기지 말고 운영 규칙으로 승격한다.

예를 들면 다음과 같다.

- "Studio에서 임시 수정한 코드는 Git에 반영되지 않는다"는 학습 포인트였다면
- 다음부터는 "코드 수정은 VS Code 우선"이라는 개발 규칙으로 바꾼다

### 규칙 5

한 프로젝트에서 얻은 운영 노하우는 다음 프로젝트의 초기 문서에 복사해 시작한다.

즉, 학습일지는 개인 회고가 아니라 다음 프로젝트의 부팅 속도를 올리는 시스템이어야 한다.

## 6. 다른 애플리케이션 개발에 재사용하는 방법

이 운영 체계는 Roblox 프로젝트뿐 아니라 웹 앱, 모바일 앱, 자동화 도구, AI 앱에도 적용할 수 있다.

재사용 시 바뀌는 것은 기술 스택이고, 유지되는 것은 운영 방식이다.

### 유지할 것

- 티켓 단위 개발
- 완료 기준 우선 작성
- 검증 후 완료 처리
- 작업 직후 학습기록 작성
- 반복 실수의 운영 규칙화

### 프로젝트마다 조정할 것

- 폴더 구조
- 테스트 방식
- 배포 방식
- 데이터 모델
- 사용 도구와 환경

### 재사용 절차

1. 새 프로젝트용 `프로젝트개요.md`를 만든다.
2. 공통 템플릿을 복사해 `티켓단위_개발수행문서.md`를 만든다.
3. 같은 구조로 `학습기록.md`를 만든다.
4. 본 문서를 운영 기준으로 둔다.
5. 첫 번째 티켓은 항상 개발 환경과 동기화 전략 확정으로 시작한다.

## 7. 권장 운영 루틴

### 일일 루틴

- 오늘 진행할 티켓 1~3개 확인
- 선행 조건과 완료 기준 다시 확인
- 구현
- 검증
- 학습일지 작성
- 다음 작업의 리스크 메모

### 주간 루틴

- 완료 티켓 점검
- Blocked 티켓 해소 여부 확인
- 반복된 실수 정리
- 운영 규칙 수정 여부 판단
- 다음 주 우선순위 재조정

### 프로젝트 마감 루틴

- 가장 효과적이었던 개발 방식 정리
- 반복적으로 막혔던 지점 정리
- 다음 프로젝트에 복사할 템플릿 정리
- 폐기할 규칙과 유지할 규칙 구분

## 8. 바로 사용할 수 있는 시작 세트

새 프로젝트를 시작할 때는 최소한 아래 네 문서를 준비한다.

| 문서 | 역할 |
|------|------|
| 프로젝트개요.md | 무엇을 만드는지 정의 |
| 티켓단위_개발수행문서.md | 어떤 순서로 구현할지 정의 |
| 학습기록.md | 무엇을 배웠는지 축적 |
| 개발시스템_및_학습일지_운영매뉴얼.md | 어떻게 운영할지 정의 |

시작 문장은 아래처럼 단순하게 잡아도 충분하다.

- 프로젝트 목표 1문장
- MVP 범위 5줄 이내
- 첫 티켓 3개
- 학습기록 작성 규칙 5개

---

## 9. 결론

좋은 개발 시스템은 복잡한 관리 도구가 아니라, 작은 작업을 계속 전진시키는 구조여야 한다.
좋은 학습일지 시스템은 단순 기록이 아니라, 다음 프로젝트의 시행착오를 줄여주는 재사용 자산이어야 한다.

앞으로 새로운 애플리케이션을 개발할 때도 아래 한 줄을 기준으로 삼는다.

`작업은 티켓으로 쪼개고, 배움은 기록으로 남기며, 반복되는 판단은 운영 규칙으로 승격한다.`
