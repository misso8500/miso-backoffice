# Miso Backoffice 개발원칙서

## 착수와 완료

1. [README의 제품 범위](../README.md), 이 원칙서, [디자인원칙서](ui-style-conventions.md)를 읽고 현장에서 필요한 업무 흐름과 완료 기준을 정한다. 수급자 관리 MVP 범위와 기존 화면·데이터 동작을 확인한 뒤 변경 범위를 티켓으로 고정한다.
2. 기존 코드의 역할을 따른다. 화면과 상호작용은 `src/`, 여러 실행 환경에서 공유하는 업무 규칙은 `shared/`, 인증·데이터 접근과 저장은 `server/` 계층에서 다룬다. 수급자·계약·업무 등 각 영역의 규칙은 관련 코드에서 관리하고 공통 동작은 기존 구현을 재사용한다.
3. 데이터 변경은 기존 기록과 서버의 인증·접근 정책을 기준으로 설계한다. 여러 저장이 함께 성공해야 하는 경우 트랜잭션을 사용하고 실패 후 재시도와 중복 요청이 기록에 미칠 영향을 확인한다. 기본 운영 경로는 Supabase PostgreSQL이며, SQLite는 로컬 검증에 사용한다. 두 저장 경로에 영향을 주는 변경은 각각 호환성을 확인한다.
4. 실제 업무 흐름과 오류·빈 상태를 검증한다. 변경 범위에 맞춰 관련 테스트와 타입 검사 또는 빌드를 실행하고, 수행한 검증과 남은 검증을 티켓에 남긴다.
5. 문서는 기존 [티켓단위 개발문서](<티켓단위 개발문서.md>)와 [개발·학습일지 작성 기준](<개발-학습일지 시스템.md>)을 따른다. 사용법이나 운영 절차가 달라지면 해당 기능 문서를 갱신하고, 검증과 판단 근거는 기존 [학습기록](학습기록.md)에 연결한다.

## 데이터 조회 병목과 메모리 관리

목록·검색·집계, 여러 데이터의 결합, 파일 조회·가져오기·내보내기를 추가하거나 변경할 때 티켓의 설계와 검증에 아래 기준을 적용한다.

### 조회 범위와 병목 측정

- 착수 시 브라우저 → API → DB 또는 외부 서비스의 조회 흐름을 그린다. 화면에서 실제로 필요한 필드와 행, 기간·상태·검색 조건, 정렬 기준과 최대 조회량을 정한다. 예를 들어 수급자 목록은 요약 필드를 먼저 조회하고 이력과 서류는 상세에서 요청한다. 월간 업무와 본인부담금은 선택 월을 조회 범위로 삼는다.
- 필터·정렬·집계는 데이터가 있는 쪽에서 처리하고 필요한 결과만 반환한다. 누적형 목록은 서버에서 페이지 크기를 제한하고 동률에서도 순서가 일정하도록 고유 키를 정렬에 포함한다. 일부 행만 로드하는 화면에서 전체 건수나 합계를 표시한다면 해당 필터를 적용한 전체 범위에서 계산한다.
- 요청마다 반복되는 SQL이나 외부 호출, 행별 추가 조회(N+1), 넓은 스캔, 과도한 응답, 렌더링 비용을 확인한다. 브라우저 네트워크와 성능 기록, API 처리 시간, DB 쿼리 횟수와 실행 계획으로 느린 구간을 찾는다. 인덱스나 캐시를 추가할 때는 실제 필터·정렬과 측정 결과를 근거로 삼는다.

### 서버와 브라우저의 메모리 수명

- 파일이나 대량 이력은 서버가 동시에 보관할 데이터량을 제한한다. 업로드 크기와 처리 단위를 정하고, 포맷과 실행 환경이 지원하면 스트리밍 또는 배치로 처리한다. 펼친 파일, 파싱 결과, 응답 데이터가 여러 복사본으로 동시에 남는지 확인하고 외부 요청의 동시 실행 수를 제한한다.
- 브라우저는 현재 화면에서 사용할 목록과 파일만 불러온다. 화면을 닫거나 조건을 바꿀 때 불필요한 요청을 취소하거나 이전 응답을 무시한다. 이미지·PDF 미리보기의 Blob URL은 사용을 마치면 해제한다. 대량 목록의 렌더링이 병목으로 확인되면 페이지 크기와 DOM에 그리는 행 수를 점검한다.
- 캐시는 기존 구현을 우선 확인한다. 새로 추가하거나 범위를 넓힐 때는 캐시 키에 영향을 주는 필터와 접근 범위, 보관 기한과 상한, 저장 후 무효화, 로그아웃·계정 변경 시 정리를 정한다. 개인정보와 문서 원본은 브라우저 영속 캐시나 성능 로그에 저장하지 않는다.

### 티켓에서 확인할 결과

- 합성 데이터로 통상 규모와 예상 누적 규모를 재현한다. 티켓에 데이터 행 수·기간·파일 크기와 해당 작업의 완료 기준을 정하고, 같은 조건에서 변경 전후 또는 설정한 목표를 비교한다.
- 병목에 해당하는 지표를 남긴다. 예를 들어 목록은 요청·쿼리 횟수, 응답 크기와 처리 시간, 대량 파일은 서버의 최대 메모리 사용량, 미리보기는 열기·닫기 반복 후 메모리 추세를 확인한다. UI에서 날짜나 검색 조건을 빠르게 바꿔도 최신 결과가 표시되는지 확인한다.
- SQLite 결과는 로컬 기능 검증에 사용한다. 운영 쿼리 성능과 서버리스 메모리 한도가 완료 판단에 필요하면 대표적인 데이터와 배포 조건을 재현한 PostgreSQL·서버 환경에서 확인하고, 검증 환경과 결과를 티켓에 남긴다.
