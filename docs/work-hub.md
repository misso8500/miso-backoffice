# 공동 업무 사용 안내

## 주·월간 개괄 (WH-003)

상단 보라색 고정 탐색 바의 **일간·주간·월간**으로 전환한다. 화살표는 선택한 보기 단위로 이동하고, 날짜 입력은 기준 날짜를 지정한다. **오늘로**는 보기를 유지한 채 오늘이 속한 기간으로 이동한다. 주간은 월요일~일요일이며 월간은 인접 달을 포함한 6주를 표시한다. 월간 상단 건수는 선택한 달만 집계한다.

- 보라색 **계획**, 초록색 **수행**, 노란색 **마감**을 구분한다. 주간은 조회한 한 주 전체에서 같은 업무·담당자에 수행이 있으면 수행만, 없으면 계획만 표시한다. 계획이나 수행이 있는 업무는 마감 카드에서 제외한다. 서로 다른 담당자의 진행 상태는 따로 남기며, 여러 날짜에 수행했다면 각 실제 날짜의 기록을 유지한다. 상단 건수도 표시된 기록 기준이다. 월간도 해당 월 단위로 같은 우선순위를 적용하며 인접 달의 기록은 선택한 달의 카드를 숨기지 않는다. 수행은 실제 내용과 실제 날짜를 사용하며 시간대 미확인은 그대로 표시한다.
- 담당자 필터의 순서는 **신수연 → 박준규 → 황영상**이다. 전체 구성원 보기에서는 카드 좌상단에 흰색 원형 **ㅅ·ㅂ·ㅎ** 스티커가 카드 밖으로 조금 돌출된다. 이름도 함께 표기한다. 담당자 미정은 `?`, 과거 계정 배정은 기존 계정 이름을 사용한다.
- 날짜를 누르면 해당 날짜·현재 담당자 조건으로 일간에 들어간다. 개별 기록을 누르면 기록의 실제 수행자 조건으로 들어간다. 업무의 현재 담당자를 바꿔도 과거 계획·수행 담당자는 바뀌지 않는다.
- 하단 **날짜를 정할 업무**는 현재 담당자 조건에서 활성 계획이 하나도 없는 진행 업무다. 조회 기간 밖에 계획이 있는 업무도 제외한다. 기한이 있어도 계획이 없으면 이 목록과 마감 카드에 함께 나타날 수 있다. 카드를 누른 뒤 일간에서 계획을 배치한다.
- 취소된 계획·수행은 달력에서 제외하며 일간의 취소 기록에서 확인한다. 완료·취소된 업무는 마감 예정에 나오지 않지만 이미 기록한 실제 수행은 남는다. 빈 날짜는 단지 등록된 기록이 없다는 뜻이다.

기존 업무/계획/수행 데이터를 조회하고 달력용 복제 테이블을 만들지 않는다. `GET /api/work/calendar`는 인증된 허용 계정만 사용하며, 날짜·담당자와 최대 62일 조회 범위를 검증한다. 이번 단계는 DB 구조 변경이 없으며 새 API 경로를 쓰려면 기존 API 서버를 재시작한다.

전체 **104개 테스트와 빌드 통과**. 주·월 경계와 윤년·말일·지원 날짜 경계, 담당자 변경 전 기록 보존, 다른 기간의 계획 제외, 취소·완료 집계, 인증과 잘못된 조회 거절, API 재시작 후 복원을 확인했다. 실제 운영 Postgres와 로그인 브라우저·모바일 렌더링은 미검증이다. 운영 DB 변경과 배포는 하지 않았다.

## 일간 계획·실제 수행 (WH-002)

상단 날짜 바에서 이전/다음 날, 날짜 직접 지정, 오늘로 이동한다. 담당자 필터를 바꾸면 업무 목록과 일간 계획/수행이 함께 좁혀진다. 담당자 미정 필터에서는 업무 목록만 미배정으로 좁히고, 계획/수행은 전체 담당자를 표시한다고 안내한다.

1. 업무 카드의 **계획**에서 수행할 사람, 날짜, 오전/오후/미정을 선택한다. 같은 업무라도 날짜와 사람이 다르면 별도의 계획을 남길 수 있다. 같은 사람·날짜의 중복 계획은 거절한다. 재배치는 계획을 취소한 뒤 새로 배치한다.
2. 계획 카드의 **오전/오후**를 누르면 그 사람·계획 날짜에 실제 수행을 기록한다. 제목을 초기 수행 내용으로 사용하며 상세 내용은 실제 수행 카드에서 보완한다. 같은 버튼 재클릭은 중복 기록을 만들지 않고, 다른 시간대 선택은 버전을 확인한 뒤 시간대만 바꾼다.
3. **계획 없이 수행 남기기**에서는 수행자·실제 날짜·시간대·내용·분류·관련자를 지정한다. 기존 업무 카드의 **수행 기록**은 그 업무와 분류·관련자를 연결한다.
4. 실제 수행의 **내용 수정**은 수행 내용과 시간대를 바꾼다. 날짜와 수행자를 잘못 기록했다면 취소 후 다시 기록한다. 미확인 시간대는 오전/오후에 임의로 배분하지 않는다. 미래 날짜에는 계획만 남길 수 있다.
5. 계획 취소는 해당 계획을 타임라인에서 숨기고 기존 수행은 남긴다. 수행 취소도 계획·업무 전체 상태를 변경하지 않는다. 취소 내역은 하단의 **취소된 기록**에서 확인한다. 현재 취소 복원 버튼은 없으며 새 기록으로 다시 남긴다.
6. **업무 전체 완료**와 **다시 진행**은 업무 해결 상태만 바꾼다. 계획·수행을 만들거나 지우지 않는다. 완료된 업무는 `완료됨` 필터에서 확인하고 다시 진행해야 새 계획을 배치할 수 있다. 기존 계획은 보존되므로 불필요해진 미래 계획은 별도로 취소한다.

업무 제목의 보라 형광펜은 선택일 계획, 초록 형광펜은 선택일 실제 수행을 뜻한다. 둘 다 있으면 수행 색을 우선하고 계획/수행 건수를 함께 표시한다. 조회 중에는 이전 날짜/담당자의 기록을 새 날짜에 표시하지 않는다.

실제 수행자(신수연·박준규·황영상)와 입력한 로그인 계정은 다르다. 허용 계정은 다른 담당자의 실제 수행도 대신 기록할 수 있고 입력자 ID는 서버가 기록한다. 출근·인정시간·휴가 사용이나 공식 일지 검토 완료를 자동 판정하지 않는다.

계획/수행은 당시 제목·분류·관련자를 보존한다. 이후 원래 업무의 제목이나 담당자를 고쳐도 과거 스냅샷을 다시 쓰지 않는다. 새 계획이나 업무에서 직접 남기는 새 수행은 그 시점의 업무 정보를 사용한다.

### 추가 저장 구조와 검증

`work_plans`, `work_executions`, `work_journal_events`를 추가했다. `work_tasks.completed_at`은 업무 전체 완료를 표시하며 기존 상태 제약을 파괴하지 않고 기존 DB에 열을 추가한다. 계획/수행과 이력은 같은 트랜잭션으로 저장한다. Postgres 변경은 업무 행을 먼저 잠가, 업무 취소와 새 계획/수행 입력이 엇갈려 남지 않게 한다.

WH-002 구현 시점에 전체 검사 **99개와 빌드가 통과**했다. 계획 중복, 빠른 수행의 동시 요청/재시도, 시간대 변경 버전 충돌, 취소 후 수행 보존, 직접 수행, 스냅샷 보존, 업무 완료/재개, 이력 실패 시 원복, API 재시작 후 유지를 검사했다. 실제 운영 Postgres·실제 Google 계정 화면·모바일 렌더링은 미검증이다. Postgres 어댑터 검사는 SQLite 브리지이며 실제 PostgreSQL 동시성 검증을 대신하지 않는다.

API를 재시작해야 새 경로와 스키마가 적용된다. 이번 검증은 임시 DB와 가짜 인증 서버로 수행했고 운영 DB는 변경하지 않았다.

## 사용할 수 있는 기능

사이드바의 **공동 업무**에서 제목·담당자·기한·분류·상세 내용을 등록한다. 내용만 먼저 남기고 담당자와 분류를 나중에 보완할 수도 있다. 요청자는 현재 로그인 계정으로 서버가 기록한다.

기존 로그인 허용 계정 모두가 업무를 조회·수정·취소한다. 별도의 직책별 결재 권한은 없다. 담당자 필터는 보기 조건이며 접근 제한을 뜻하지 않는다.

로그인 구성원은 서버의 `AUTH_ALLOWED_EMAILS`를 기준으로 생성한다. 첫 로그인 전에는 이메일로 표시되며, 해당 계정이 공동 업무에 처음 접근하면 Google 이름을 반영한다. 이는 요청자·수정자를 확인하는 계정 명부다. 기존 수급자 담당자 명부와 이름으로 병합하지 않는다. 하나의 이메일에 연결된 Google 사용자 ID가 바뀌면 자동 재연결하지 않고 오류로 알린다.

업무 담당자 명부는 로그인 계정과 별도로 **신수연 → 박준규 → 황영상** 세 명을 고정 순서로 제공한다. 등록·수정과 담당자 필터에서 같은 목록을 사용한다. 역할 설명과 `(나)`는 표시하지 않으며 Google 이름/로그인 순서로 명단을 바꾸지 않는다. 계정과 고정 담당자의 자동 연결은 하지 않는다.

이전 버전의 계정 기반 배정은 보존한다. 기존 업무를 편집할 때 기존 배정은 유지하거나 세 명 중 하나로 재배정할 수 있으며, 새 업무에는 고정 명부만 배정할 수 있다.

## 관련자 연결과 간단 등록

수급자/근로자를 이름·구분 정보로 검색하고 여러 명 연결한다. 근로자는 기존 **근로계약 ID**로 연결하며 같은 이름의 계약은 기간을 보고 구분한다. 이 단계에서 계약 갱신을 가로지르는 새로운 직원 통합 명부를 만들지는 않는다. 검색 결과에는 연락처·주민번호·계좌를 내려주지 않는다.

없는 사람은 이름과 선택적 연락처로 간단 등록할 수 있다. 이는 시안의 가상 등록과 달리 기존 수급자/근로계약 명부에 **실제 초안**을 저장한다. 업무를 저장하지 않거나 편집 취소해도 명부 초안은 유지된다. 나머지 정보는 해당 관리 화면에서 보완한다. 같은 이름의 기존 기록이 있으면 확인을 요청하고 자동 병합하지 않는다.

업무 분류는 센터 운영을 정리하는 초안이다. 공식 공단 평가지표의 충족이나 증빙 확보를 판정하지 않는다.

## 수정·취소와 변경 이력

- 수정은 불러왔던 버전을 함께 보내고, 다른 사람이 먼저 수정했다면 덮어쓰지 않는다.
- 오류 시 입력은 폼에 유지된다. 목록 새로고침은 폼을 덮어쓰지 않는다. 최신 업무의 수정 버튼으로 다시 시작할 때 입력 변경 여부를 확인한다.
- 등록은 요청 식별자를 사용해 통신 오류 후 같은 내용 재시도로 중복 생성되지 않게 한다. 이미 처리된 요청의 내용까지 바꿔 다시 전송하면 409로 알린다.
- 취소는 실제 삭제가 아니라 상태 변경이다. 기본 목록에서 사라지고 `취소됨` 필터로 다시 볼 수 있다. 첫 단계에는 취소 복원 기능이 없다.
- 각 카드의 변경 이력에서 등록·수정·취소 당시 내용, 담당자, 기한, 관련자, 작성 계정을 확인한다. 업무와 이력은 한 트랜잭션으로 저장한다.

## 실행·DB 적용

프런트엔드는 기존 `npm run dev`, API는 `npm run api`로 실행한다. 기본 API 실행은 server/shared 변경을 감지해 자동 재시작한다. 환경 파일을 바꾸거나 예전 실행 명령으로 켜 둔 서버는 직접 재시작해야 한다. 이미 켜져 있던 API는 새 코드를 사용하도록 재시작해야 한다. 초기 공동 업무 API가 없다면 화면에 재시작 안내가 표시된다.

Postgres는 기존 시작 시 스키마 적용 경로와 `npm run supabase:init` 경로에 새 테이블이 포함되어 있다. 다음 API 시작/명시적 초기화 시 적용된다. 운영 DB를 대상으로 실행하기 전 연결 환경을 확인한다. 이번 개발 검증에서는 실제 운영 Postgres를 실행하거나 데이터를 변경하지 않았다.

테이블은 `work_members`(인증 계정), `work_assignees`(고정 담당자), `work_tasks`, `work_task_events`다. `work_tasks.roster_assignee_id`에 새 담당자를 연결하고, 기존 `assignee_id`는 과거 배정을 보존한다. Postgres에는 RLS를 활성화하고 anon/authenticated의 직접 접근을 차단했다. 데이터는 인증된 자체 API를 거친다. SQLite 로컬 검증에도 동일 업무 구조를 적용한다.

## 검증 및 다음 단계

- 전체 `node --test tests/*.test.mjs`: **92개 통과**.
- `npm run build`: TypeScript/Vite 빌드 통과. 기존 번들 크기 안내는 남아 있다.
- HTTP 통합: 임시 SQLite 파일·가짜 Google 인증 서버로 3계정 공동 수정, 관련자 초안 연결, 중복 재시도, 버전 충돌, 취소, API 재시작 후 유지, 변경 이력 확인.
- 저장소 검사: 이벤트 저장 실패 시 업무 변경 원복. Postgres 어댑터의 트랜잭션 경계와 공통 SQL은 SQLite 브리지로 검사했다. 실제 Postgres에서의 런타임/동시성 검증을 대체하지 않는다.
- 실제 계정 로그인 후 화면 조작과 모바일 배치는 별도 검토 대상이다.

고정 담당자 보완은 관련 검사 6개와 빌드를 통과했다. 로그인 이름/순서와 무관한 명단 순서, 기존 DB 열 추가, 과거 배정 보존·재배정, 고정 명부 밖 신규 배정 거절을 확인했다. 실제 운영 DB에 이 변경을 적용하지는 않았다.

일간 계획·수행과 주·월 캘린더를 구현했다. 다음 WH-004는 실제 수행을 업무일지 초안 검토로 연결한다. 출근부·업무수행일지·휴가신청서의 공식 서식 생성은 아직 구현하지 않았다.

## 일간 API 오류 보완 (2026-10-19)

계획·수행 API가 추가되기 전에 실행한 로컬 서버는 새 경로를 알지 못했다. 화면의 불러오기는 서버 코드를 다시 읽지 않으므로 같은 404가 반복되었다. 실제 실행 중인 서버를 최신 코드로 재시작했고, 기본 npm run api에 변경 감지를 적용해 같은 원인의 재발을 줄였다.

한글/영문 구버전 API 오류 모두에서 로컬은 서버 재실행, 배포 환경은 최신 API 배포가 필요함을 안내한다. 일간 조회 실패 시 빈 기록이나 0건처럼 표시하지 않으며, 조회 완료 전에는 업무 카드의 계획·수행 버튼을 비활성화한다. 방어 검사에서도 원래 오류를 일반적인 ‘먼저 불러오기’ 안내로 덮어쓰지 않는다.

전체 106개 검사와 빌드 통과. 임시 DB HTTP 검사에서 계획·수행 등록을 확인했고, 실제 로컬 API 시작과 파일 변경에 따른 자동 재시작 로그도 확인했다. 실제 계정의 브라우저 저장 동작은 미검증이다.

### 주간 표시 우선순위 보완

주간보기의 중복 색상 혼란을 줄이기 위해 수행 → 계획 → 마감 순서로 표시 종류를 선택한다. 취소된 수행은 계획으로, 계획도 취소되면 남아 있는 마감 예정으로 돌아간다. 원래 계획과 기한은 저장 데이터에서 지우지 않으며 일간에서 계속 확인한다. 판정 범위는 현재 조회한 한 주이고 업무 전체 완료 상태와는 별개다. 관련 달력 검사 6개와 빌드를 통과했다.

### 월간 표시 우선순위 보완

월간에도 수행 → 계획 → 마감 순서를 적용했다. 인접 달을 포함한 6주 달력에서는 월별로 따로 판정해 다음 달 수행이 이번 달 계획을 숨기지 않게 한다. 상단 건수는 선택한 달의 표시된 기록만 집계한다. 관련 달력 검사 7개와 빌드를 통과했다.
