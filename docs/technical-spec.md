# 개발 명세서

## 1. 문서 목적

이 문서는 `miso-backoffice` 프로젝트의 초기 개발 범위, 기술 방향, 도메인 모델, 핵심 기능 요구 사항을 정의한다.

이 명세서는 다음 목적을 가진다.

- MVP 범위를 명확히 한다.
- 1인 개발 기준으로 과도한 기술 선택을 방지한다.
- 이후 확장될 도메인을 고려한 최소 구조를 정리한다.
- 티켓 단위 구현의 기준 문서로 사용한다.

## 2. 프로젝트 개요

- 프로젝트명: `miso-backoffice`
- 대상: 미소 노인재가복지센터 백오피스 웹
- 현재 목표: 수급자 관리 MVP 구현
- 장기 목표: 수급자, 근로자, 근로계약, 임금, 근태, 고객 관리까지 확장 가능한 운영 시스템 구축

## 3. 개발 원칙

- 1인 개발에 적합한 단일 프로젝트 구조를 우선한다.
- 프론트엔드와 서버 로직을 가능한 한 한 저장소, 한 실행 흐름 안에서 관리한다.
- Python은 본 프로젝트의 기본 구현 스택으로 채택하지 않는다.
- 구현과 함께 문서를 누적하되, 문서는 실제 개발을 돕는 수준으로 유지한다.
- 초기에는 과도한 추상화보다 반복 가능한 패턴을 우선한다.

## 4. 권장 기술 방향

현 시점 기준 권장 기술 방향은 아래와 같다.

- 프레임워크: Next.js
- 언어: TypeScript
- 데이터베이스: PostgreSQL
- ORM: Prisma
- 인증: Auth.js
- UI 구성: 백오피스에 적합한 검증된 컴포넌트 조합 사용
- 폼 검증: 스키마 기반 검증 도입

이 방향을 채택하는 이유는 다음과 같다.

- 처음 배우는 개발자도 자료를 찾기 쉽다.
- 백오피스 개발에 필요한 폼, 테이블, 검색, 권한 패턴이 풍부하다.
- 도메인이 늘어나도 같은 방식으로 화면과 데이터를 확장하기 쉽다.
- 프론트와 백을 분리했을 때 생기는 초기 학습 비용을 줄일 수 있다.

## 5. 현재 MVP 범위

현재 단계에서는 수급자 관리 도메인만 우선 구현한다.

### 5.1 포함 범위

- 수급자 정보 CRUD
- 담당 관리자 배정
- 담당자 기준 수급자 목록 조회
- 계약 만료일 경고 표시
- 검색, 필터, 정렬의 기초 기능
- 로그인 및 최소 역할 구분

### 5.2 제외 범위

- 근로자 관리
- 근로계약 관리
- 임금 관리
- 근태 관리
- 고객 관리
- 고급 통계 및 대시보드
- 복잡한 조직 권한 체계
- 외부 연동

제외 범위는 이번 MVP에서 구현하지 않지만, 이후 동일한 구조 안에서 확장될 수 있어야 한다.

## 6. 사용자 및 권한

초기 MVP에서는 최소 권한 모델만 적용한다.

### 6.1 사용자 역할

- `admin`
  - 전체 수급자 조회 가능
  - 수급자 생성, 수정, 삭제 가능
  - 담당자 배정 가능
- `manager`
  - 자신에게 배정된 수급자 조회 가능
  - 허용된 범위 내 수급자 수정 가능

### 6.2 권한 원칙

- 인증되지 않은 사용자는 내부 페이지에 접근할 수 없다.
- 관리자는 자신에게 허용된 데이터만 조회할 수 있어야 한다.
- 권한 체크는 UI 수준과 서버 수준 모두에서 반영되어야 한다.

## 7. 기능 요구 사항

### 7.1 수급자 정보 관리

수급자의 기본 정보를 등록, 조회, 수정, 삭제할 수 있어야 한다.

필수 필드 초안:

- 이름
- 등급
- 생년월일
- 주소
- 계약 시작일
- 계약 종료일
- 담당 관리자

기능 요구:

- 수급자 등록
- 수급자 목록 조회
- 수급자 상세 조회
- 수급자 수정
- 수급자 삭제
- 입력값 유효성 검사

### 7.2 담당자 배정 및 조회

- 수급자는 한 명의 담당 관리자와 연결된다.
- 관리자는 자신이 담당하는 수급자 목록을 조회할 수 있어야 한다.
- 관리자는 수급자 목록에서 담당자 정보를 확인할 수 있어야 한다.

### 7.3 계약 만료 경고

계약 종료일을 기준으로 상태를 계산한다.

- `normal`: 계약 종료일까지 16일 이상 남은 상태
- `expiring`: 계약 종료일까지 15일 이하 남은 상태
- `expired`: 계약 종료일이 지난 상태

기능 요구:

- 목록에서 상태를 배지 또는 강조 형태로 표시
- 상태 기준으로 필터 가능
- 상태 계산 기준이 명확하게 코드로 분리되어야 함

### 7.4 검색, 필터, 정렬

초기 MVP에서 제공할 검색/필터 기능:

- 이름 검색
- 등급 필터
- 계약 상태 필터
- 담당자 기준 조회

정렬 항목 예시:

- 이름
- 계약 종료일
- 생성일

### 7.5 인증 및 접근 제어

- 로그인 기능 제공
- 세션 기반 또는 프레임워크 표준 인증 방식 채택
- 로그인 후 역할에 따라 접근 가능한 데이터가 달라져야 함

## 8. 데이터 모델 초안

### 8.1 User

- `id`
- `name`
- `email`
- `password` 또는 인증 제공자 정보
- `role`
- `createdAt`
- `updatedAt`

### 8.2 Manager

초기에는 `User`와 동일 개념으로 시작할 수 있으며, 필요 시 별도 프로필 모델로 분리한다.

예시 필드:

- `id`
- `userId`
- `displayName`
- `employmentStatus`

### 8.3 Recipient

- `id`
- `name`
- `grade`
- `birthDate`
- `address`
- `contractStartDate`
- `contractEndDate`
- `managerId`
- `createdAt`
- `updatedAt`

## 9. 화면 요구 사항

초기 MVP의 기본 화면은 아래와 같다.

- 로그인 페이지
- 수급자 목록 페이지
- 수급자 등록 페이지
- 수급자 상세 페이지
- 수급자 수정 페이지

목록 페이지 기본 구성:

- 검색 입력
- 필터 영역
- 정렬 기준
- 목록 테이블
- 만료 상태 표시

폼 화면 기본 구성:

- 필수 입력 항목 표시
- 날짜 입력 검증
- 저장/취소 동작
- 검증 오류 메시지 표시

## 10. API/서버 동작 기준

구현 방식은 프로젝트 구조에 따라 달라질 수 있으나, 서버 동작은 아래 책임을 가져야 한다.

- 수급자 CRUD 처리
- 권한 검증
- 검색/필터/정렬 처리
- 계약 상태 계산 또는 계산에 필요한 데이터 제공
- 폼 입력 유효성 검증

예상 API 범위 예시:

- `GET /api/recipients`
- `POST /api/recipients`
- `GET /api/recipients/:id`
- `PATCH /api/recipients/:id`
- `DELETE /api/recipients/:id`
- `GET /api/managers`
- `POST /api/auth/sign-in`

## 11. 비기능 요구 사항

- 반응형으로 동작해야 한다.
- 내부 업무용 서비스 기준으로 빠르게 탐색 가능한 UI를 제공해야 한다.
- 기능 추가 시 동일한 구조로 도메인을 확장할 수 있어야 한다.
- 사용자 입력 검증과 기본 보안 방어를 적용해야 한다.
- 핵심 비즈니스 규칙은 재사용 가능한 함수 또는 서버 로직으로 분리해야 한다.

## 12. 확장 고려 사항

향후 아래 도메인이 추가될 가능성을 전제로 구조를 잡는다.

- 근로자 관리
- 근로계약 관리
- 임금 관리
- 근태 관리
- 고객 관리

따라서 초기부터 아래 원칙을 고려한다.

- 도메인별 폴더 분리 가능 구조
- 공통 테이블/폼 패턴 재사용
- 권한 로직의 재사용성
- 날짜 및 상태 계산 로직의 모듈화

## 13. 완료 기준

수급자 관리 MVP는 아래 조건을 만족하면 완료로 본다.

- 로그인 후 권한에 맞는 페이지 접근이 가능하다.
- 수급자 등록, 조회, 수정, 삭제가 정상 동작한다.
- 담당자 배정이 가능하다.
- 계약 만료 상태가 목록에서 올바르게 표시된다.
- 이름, 등급, 계약 상태 기준 검색/필터가 가능하다.
- 이후 도메인 추가가 가능한 기본 구조가 확보되어 있다.
